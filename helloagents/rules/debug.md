# 调试规则

本模块定义调试（修复 bug、排查失败测试、处理异常行为）的执行规则。
作为 develop.md 失败处理、~test 失败、~verify 修复循环的方法论补充。
失败处理场景加载：按 G7 按需读取表"调试时"行加载。

---

## 铁律

```yaml
- 禁止未经根因分析直接修复症状
- 没有可运行、可重复、可判断的反馈循环，不直接猜原因或改代码
- 一次只改一个变量（单变量测试），否则无法定位真正的修复点
- 修复针对根因，不是症状；症状修补会留下同级调用方仍损坏
```

---

## Git 作为记忆

```yaml
每次调试前先读 git 历史，避免重复失败方向:
  - git log --oneline -20（最近变更）
  - git log --all --grep="revert"（过去的失败回滚）
  - git log --all --grep="fix" -p <相关文件>（该文件历史修复）
发现之前已尝试并回滚过类似修复 → 不要重复同一方向
```

---

## 反馈循环优先

```yaml
反馈循环是调试入口，必须能证明"问题出现 / 问题消失":
  - 优先写失败测试复现 bug
  - 不适合写测试时用替代手段: HTTP 脚本 / CLI 样例输入 / 浏览器脚本 / 请求回放 / 最小验证脚本 / 差异对比
  - 循环要快、稳定、断言具体症状，不用"没有崩溃"代替正确性
  - 非确定性问题先提高复现率: 记录触发次数、失败比例、关键条件
  - 无法建立循环时停止，说明已尝试方式，向用户请求日志/录屏/请求记录/环境访问
```

---

## 四阶段调试法

```yaml
1. 定位:
   - 完整读取错误信息（不截断、不猜测）
   - 用反馈循环稳定复现问题（确定触发条件）
   - 反向追踪数据流（从错误点向上游追溯）

2. 分析:
   - 找到类似的正常工作代码，对比差异
   - 检查最近变更（git log / git diff）
   - 识别所有隐含假设

3. 假设:
   - 形成 3-5 个按可能性排序的假设
   - 每个假设必须可证伪: "如果原因是 X，那么改变或观测 Y 会出现 Z"
   - 单变量测试（一次只改一个东西）
   - 记录每次尝试和结果

4. 修复:
   - 先写失败测试复现 bug（如可行）
   - 实现最小修复（针对根因，不是症状）
   - 验证修复有效且无回归
   - 在共享函数中一次性修复根因（追溯全部调用方，不只修报告命中的路径）
```

## 临时观测点

```yaml
- 临时日志必须带唯一前缀，如 [DEBUG-a4f2]
- 禁止"到处打印再搜索"; 每个观测点都要对应一个假设
- 收尾前搜索前缀，删除所有临时日志、临时验证脚本和实验文件
- 确需保留时移动到明确的 debug 目录并说明原因
```

---

## 卡住升级阶梯

```yaml
连续修复失败时按阶梯升级（对抗"反复试同一方向"的常见毛病）:

第 1-2 次失败: 正常反思，调整修复方向
第 3 次失败: 停止。3 次失败意味着可能是架构问题而非局部 bug。
  重新从根因分析开始，质疑当前方向是否正确
第 4 次失败: 扩大范围——重读所有相关文件，审查 git 历史中的相关变更，
  检查是否有隐藏依赖或副作用
第 5 次失败: 必须与用户讨论，提供选项:
  1. 组合之前接近成功的尝试
  2. 尝试完全相反的方向
  3. 重构架构而非继续局部修补
  4. 重新定义问题

超过 5 次: 停止自主尝试，转为用户决策
```

## 与现有失败处理的关系

```yaml
- develop.md 步骤6"反复失败→break-loop 5维度根因分析"、~verify"修复循环最多3轮"
  均是具体场景的失败计数，本文件提供统一的方法论
- 本文件不改变上述计数值，只补充"失败时该怎么想、怎么查"的步骤
- 状态机触发: 调试阶段不改 WORKFLOW_MODE/CURRENT_STAGE，复用调用方的失败处理流程
```

## 交付检查

- [ ] 根因已识别并记录（不是症状）
- [ ] 已建立能证明"问题出现 / 消失"的反馈循环
- [ ] 有失败测试复现 bug，或已说明无合适切入点并给出替代验证
- [ ] 单一修复针对根因，已追溯全部调用方
- [ ] 临时观测点和实验文件已清理（前缀已搜索）
- [ ] 无回归引入
