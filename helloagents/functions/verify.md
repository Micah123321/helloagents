# ~verify 命令 - 审查验证

本模块定义审查、运行验证命令、修复失败并收尾的完整验证流程。~verify 是 ~review 的超集，在代码审查基础上增加运行验证命令、自动修复和收尾归档。

---

## 命令说明

```yaml
命令: ~verify [<路径>]
类型: 场景确认类
功能: 审查代码 + 运行验证命令 + 修复失败项 + 收尾
评估: 需求理解 + EHRB 检测（不评分不追问）
```

---

## 执行模式适配

```yaml
规则:
  1. 独立工具命令，不受 WORKFLOW_MODE 影响
  2. 无参数时审查最近变更（git diff）
  3. 审查+验证+修复为连续流程
  4. 修复后自动重新验证（最多 3 轮）
  5. ≥2个分析维度或文件≥2 且并行收益明确时，应主动按编排五步法调度子代理并行 [→ G10]
```

---

## 执行流程

### 步骤1: 需求理解 + EHRB 检测

```yaml
无独立输出，直接进入下一步
```

### 步骤2: 确定验证范围

```yaml
无参数时:
  检测最近变更: git diff --stat（有未提交变更）或 git diff HEAD~1 --stat（最近一次提交）
  无变更: 输出: 完成（无变更可验证），流程结束

有参数时: 验证指定路径存在

输出: 确认（验证范围+文件数+预计检查项）
⛔ END_TURN
用户确认后: 继续 / 调整范围 / 取消(→状态重置)
```

### 步骤3: 代码审查（继承 ~review 能力）

```yaml
分析维度（独立，可并行）:
  质量: 代码复杂度、重复度、命名规范
  安全: 不安全函数、敏感信息硬编码、注入风险
  性能: 低效算法模式、资源泄漏风险
  简化/过度工程: 不必要的抽象层、重复的标准库功能、多余的配置参数、一个实现者的接口、可删除的模板代码
  视觉/UX（含 UI 代码时自动启用）: 样式可维护性、组件一致性、可访问性、布局适配

分析调度（按需自动编排 + 通用触发场景总表"代码/质量审查"场景 [→ G10]）:
  ≥2个维度或文件≥2 且并行收益明确: 应主动调用子代理并行执行
  仅1个维度且文件仅1个: 主代理直接执行
  推理强度: 若满足 Codex 编排闸门，按审查任务调用期选择 `reasoning_effort`；普通验证默认 `high`，复杂验证 `xhigh`；仅 TASK_COMPLEXITY=complex 且至少命中2个升级信号、其中至少1个来自架构/边界/风险类时使用 `max`，schema 不支持时省略并记录 fallback
  降级: 子代理失败 → 主代理直接执行审查 + tasks.md 标记 [降级执行]
  降级证据: Codex 环境下不得仅凭初始工具列表未显示 spawn_agent 或工具说明要求"显式请求"而跳过编排；降级前必须完成 G10 工具发现，并记录工具发现失败、环境前置未满足、实际调用失败或子代理超时/失败的具体原因

输出: 审查报告（按 Critical/Warning/Info 分级）
```

### 步骤4: 运行验证命令

```yaml
工具探测（≤3秒）:
  优先调用 ProjectEnvService.validationCommands(scope=verify):
    .helloagents/runbook.yaml local_iteration 或 validation.before_commit → 推荐验证命令
    未命中 → 继续读取项目配置
  读取项目配置 → 识别可用验证工具:
    lint/格式化: eslint/prettier/ruff/black 等
    类型检查: tsc/mypy/pyright 等
    单元测试: jest/pytest/vitest 等
    构建: npm run build/cargo build 等

执行策略（按顺序，失败不阻断后续）:
  1. lint + 类型检查（对变更文件）
  2. 单元测试（相关测试）
  3. 构建验证（如项目有构建命令）

结果收集:
  每项记录: 工具名、退出码、错误数、详细输出
  全部通过 → 步骤6（收尾）
  有失败 → 步骤5（修复）
```

### 步骤5: 自动修复

```yaml
修复循环（最多 3 轮）:

每轮:
  1. 分析失败项，分类:
     可自动修复: lint 格式错误、简单类型错误、缺失导入
     需手动修复: 逻辑错误、架构问题、复杂类型错误
  2. 执行自动修复（仅可自动修复项）
  3. 重新运行验证命令
  4. 判定:
     全部通过 → 步骤6
     仍有失败但减少 → 继续下一轮
     失败数不减 → 中止修复

修复记录: 每轮记录（修复项、修复方式、验证结果）

仍有失败时:
  输出: 确认（未修复列表+建议手动处理项）
  ⛔ END_TURN
  用户确认后:
    继续收尾: 带未修复项进入步骤6
    手动修复后重试: 等待用户修复 → 重新执行步骤4
    取消: → 状态重置
```

### 步骤6: 收尾

```yaml
生成验证报告:
  审查结果摘要（Critical/Warning/Info 分级）
  验证命令执行结果（通过/失败/跳过）
  修复记录（已修复/未修复）
  遗留问题列表（需手动处理项）

方案包同步（如有活跃方案包）:
  更新 tasks.md 中相关任务的验证状态

CHANGELOG 更新:
  按 CHANGELOG 记录规则记录验证活动

输出: 完成（验证报告+修复摘要+遗留问题）
→ 状态重置
```

---

## 不确定性处理

| 场景 | 处理 |
|------|------|
| 无验证工具可用 | 仅执行代码审查（步骤3），跳过步骤4~5 |
| 验证命令超时 | 标注超时，建议手动运行 |
| 修复引入新问题 | 回滚本轮修复，标注为需手动处理 |
| 审查范围过大 | 建议缩小范围或分批验证 |

---

## 交付检查

- [ ] 代码审查已实际执行并按 Critical / Warning / Info 分级
- [ ] 验证命令已实际运行并捕获退出码（未运行不得声称通过）
- [ ] 自动修复每轮已记录（修复项 / 修复方式 / 验证结果）
- [ ] 修复循环未超过 3 轮，失败数不减少时已中止（未陷入死循环）
- [ ] 遗留未修复项已在报告中列出并给出手动处理建议
- [ ] CHANGELOG 已记录验证活动（适用时）
