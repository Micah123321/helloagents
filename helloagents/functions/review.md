# ~review 命令 - 代码审查

本模块定义代码审查的执行规则。

---

## 命令说明

```yaml
命令: ~review [<路径>]
类型: 范围选择类
功能: 代码审查，可选择审查范围（全部代码/最近修改/暂存区/指定路径）
评估: 需求理解 + EHRB 检测（不评分不追问）
```

---

## 执行模式适配

```yaml
规则:
  1. 独立工具命令，不受 WORKFLOW_MODE 影响
  2. 无参数时需用户选择审查范围
  3. 审查结果按严重程度分级
  4. 发现问题时直接创建代码审查优化方案包，写入保守方案和激进方案
  5. 默认选择保守方案并进入开发实施；激进方案仅作为备选记录，用户明确指定时才执行
  6. ≥2个分析维度或审查文件≥2 且并行收益明确时，主代理应主动按编排五步法调度子代理并行审查，无需用户显式要求”子代理/并行代理” [→ G10 调用通道]
  7. 用户明确要求审查”本次改动/最近改动/最近修改/当前改动/本轮改动/这次改动”时，自动解析最近改动范围并直接进入审查，不再要求确认同一范围
  8. DEVELOP 阶段收尾的自发代码审查（验收前的自审，非显式 ~review 命令）等同 ~review 处理，满足上述编排触发条件即应主动 spawn 子代理并行审查
```

---

## 执行流程

### 步骤1: 需求理解 + EHRB 检测

```yaml
无独立输出，直接进入下一步
```

### 步骤2: 确定审查范围

```yaml
明确最近改动意图:
  触发: 参数或需求描述包含 "本次改动"、"最近改动"、"最近修改"、"当前改动"、"本轮改动"、"这次改动" 等语义
  检测顺序:
    1. git diff --name-only（工作区未提交改动）
    2. git diff --cached --name-only（暂存区改动）
    3. git diff --name-only HEAD~1..HEAD（最近一次提交）
  有变更: 设置审查范围为检测到的文件列表，直接进入步骤3执行审查
  无变更: 输出: 完成（无变更可审查）→ 状态重置
  约束: 仅在语义明确指向最近改动时跳过确认；无法解析或范围冲突时回退到下方确认流程

无参数时:
  输出: 确认（审查范围选择）
  ⛔ END_TURN
  用户确认后: 全部代码 / 最近修改 / 暂存区 / 指定路径 / 取消(→状态重置)

有参数时:
  输出: 确认（审查范围: {路径}+文件数量）
  ⛔ END_TURN
  用户确认后: 继续 / 取消(→状态重置)
```

确认回复处理:
```yaml
继承: 按 rules/state.md "确认回复匹配规则" 处理 pending 回复
继续类表达: 用户在范围确认后回复 "继续"、"确认"、"继续审查"、"开始审查" 等，直接进入步骤3执行审查
中断恢复: 范围确认页已输出但回合被用户中断时，后续继续类回复仍视为确认，不得重复输出同一审查范围确认
补充范围: 用户回复中包含新增路径、排除项或审查重点时，合并为审查上下文后进入步骤3；仅在补充内容与原范围冲突且无法自动合并时再询问
禁止: 已确认的同一审查范围不得再次要求用户确认
```

### 步骤3: 执行审查

```yaml
分析维度（独立，可并行）:
  后端/API: 接口契约、错误处理、鉴权边界、数据校验、兼容性
  前端/UI: 组件结构、交互状态、可访问性、响应式适配、视觉一致性
  迁移/持久化: 数据模型、迁移脚本、事务边界、幂等性、回滚风险
  测试/验证: 测试覆盖、断言有效性、验证命令、边界用例
  质量: 代码复杂度、重复度、命名规范、注释覆盖率
  安全: 不安全函数、敏感信息硬编码、注入风险
  性能: 低效算法模式、资源泄漏风险
  简化/过度工程（复杂度审查）:
    分析要点: 不必要的抽象层、重复的标准库功能、多余的配置参数、一个实现者的接口、可删除的模板代码、新增依赖的合理性
    输出格式: `{文件}:L{行号}` + 标签 + 简化建议
    标签: delete（可删除）, stdlib（标准库已有）, native（平台原生已有）, yagni（过度抽象/猜测性灵活度）, shrink（可精简的行数/结构）
    结束行: `net: -<N> lines possible.`（如无简化空间则输出 Lean enough.）
  视觉/UX（含 UI 代码时自动启用，按技术栈适配检查项）:
    样式可维护性: 样式组织合理、变量/主题系统使用一致、无冗余覆盖（Web: CSS 选择器特异性; 原生: 样式继承层级）
    组件一致性: 同类组件样式统一（按钮/输入框/卡片等）、设计 Token/变量使用率
    可访问性: 辅助功能标注覆盖（Web: alt/aria; 原生: accessibility label/trait）、键盘/手势导航、对比度 ≥ 4.5:1
    布局适配: 多尺寸适配逻辑合理（Web: 响应式断点; 原生: 屏幕尺寸适配）

分析调度（按需自动编排，遵循自动编排原则 + 通用触发场景总表"代码/质量审查"场景 [→ G10]）:
  ≥2个分析维度或审查文件≥2 且并行收益明确: 应主动调用子代理并行审查（子代理数=维度数或文件分组数，≤6/批）[→ G10 调用通道]
    分配原则: 可按后端/API、前端/UI、迁移/持久化、测试/验证、安全、性能等独立维度拆分；每个子代理负责≥1 个维度或文件分组，维度间无数据依赖可自由分组
    主代理职责: 汇总结果、交叉校验冲突结论、按严重程度分级、过滤重复问题；子代理失败时降级为主代理审查 + tasks.md 标记 [降级执行]
  仅1个维度且审查文件仅1个: 主代理直接执行
  所有子代理完成后: 主代理汇总 → 交叉校验 → 按严重程度分级（high/medium/low）

输出: 报告（文件路径+行号+修复建议）
```

### 步骤4: 后续操作

```yaml
无问题时:
  输出: 完成（完整审查报告+无待修复问题）
  → 状态重置

有问题时:
  1. 输出审查结果摘要（问题数量+严重程度+关键问题定位）
  2. 直接创建 plan/YYYYMMDDHHMM_code-review/ 方案包
  3. 在 proposal.md 中写入:
     - 审查结果摘要和问题列表
     - 保守方案: 最小必要修复，低风险、局部改动、保持现有行为稳定
     - 激进方案: 更大范围重构、抽象收敛或结构清理
     - 默认选择: selected_plan=conservative
     - 方案取舍: 说明激进方案仅为备选，除非用户在 ~review 输入或范围确认阶段明确指定
  4. 在 tasks.md 中仅写入保守方案对应的可执行任务；激进方案不得同时进入待执行任务列表
  5. 验证方案包完整性 [→ services/package.md validate()]
  6. 设置 STAGE_ENTRY_MODE = DIRECT, CURRENT_PACKAGE = 新建方案包路径
  7. 按 G7 按需读取表"R2 进入开发实施（入口）"加载 develop.md 和 services/package.md
  8. 进入 DEVELOP 阶段执行保守方案任务

EHRB 或阻断性问题:
  - 审查结果或修复任务触发 EHRB → 按 G2 风险确认流程中断
  - 方案包验证失败 → 输出错误或警告，按 PackageService validate() 失败处理执行
  - 开发实施失败 → 按 develop.md 失败处理执行
```

---

## 分析原则

```yaml
审查策略:
  - 测试文件降低安全检查严格度
  - 生成的代码/压缩代码跳过审查
  - 框架特定代码参考框架最佳实践
  - 复杂度难以判定时标注"需人工审查"
```

---

## 不确定性处理

| 场景 | 处理 |
|------|------|
| 文件类型无法识别 | 跳过审查，标注"未知类型" |
| 复杂度难以判定 | 标注"需人工审查" |
| 审查范围过大 | 建议缩小范围或分批审查 |

---

## 交付检查

- [ ] 审查范围已确定（全部代码 / 最近修改 / 暂存区 / 指定路径）
- [ ] 每个问题已定位到 `文件路径:行号`
- [ ] 问题已按严重程度分级（high / medium / low 或 Critical / Warning / Info）
- [ ] 简化/过度工程维度已用标签标注（delete / stdlib / native / yagni / shrink）
- [ ] 发现问题时已创建 plan/YYYYMMDDHHMM_code-review/ 方案包，含保守方案（默认）+ 激进方案（备选）
- [ ] tasks.md 仅写入保守方案任务，激进方案未混入待执行列表
- [ ] 未实际审查不得声称完成（"没有实际审查 = 不能说完成"）
