# 方案设计模块

本模块定义方案构思和详细规划的执行规则，在 R2 标准流程下执行。

**核心职责:** 收集项目上下文（Phase1）+ 设计实现方案（Phase2），生成方案包（proposal.md + tasks.md）。

---

## 模块入口

```yaml
前置: EVALUATE 阶段完成（评估确认：核心维度全部充分 或 最后一轮追问确认合一已完成）
设置: CURRENT_STAGE = DESIGN
```

---

## 执行模式适配

按 G5 执行模式行为规范，本阶段补充规则:

### 模式行为

| 模式 | TASK_COMPLEXITY=complex | TASK_COMPLEXITY=simple/moderate |
|------|----------|----------|
| INTERACTIVE | 输出方案对比→用户选择→详细规划→进入 DEVELOP | Phase1+Phase2(跳过多方案对比)→进入 DEVELOP |
| DELEGATED | 推荐方案作为选择→详细规划→进入 DEVELOP | Phase1+Phase2(跳过多方案对比)→进入 DEVELOP |
| DELEGATED_PLAN | 推荐方案作为选择→详细规划→验收→结束 | Phase1+Phase2(跳过多方案对比)→验收→结束 |

⚠️ 选择方案 = 确认执行，不再有第二次确认

### 阶段切换

```yaml
方案类型约束:
  R2 标准流程（通用路径、~auto、~plan）: 类型始终为 implementation → 进入 DEVELOP
  overview 类型: 仅限 ~exec 入口（已有方案包为 overview 时）

方案确定后:
  overview 类型（仅 ~exec 入口）:
    INTERACTIVE → 询问归档 → 归档 → 输出完成 → 状态重置
    DELEGATED → 直接归档，总结中标注
  implementation 类型:
    设置 CREATED_PACKAGE = 方案包路径
    DELEGATED_PLAN → 返回 plan.md 执行验收
    其他 → CURRENT_STAGE = DEVELOP → 按 G7 加载开发实施阶段文件 → 进入 DEVELOP
```

### 推荐方案选择（DELEGATED模式）

```yaml
策略: 综合评估维度 → 优先"推荐"标记方案 → 无推荐则选用户价值与风险综合最优
记录: 在 proposal.md 中记录选择理由
```

## 执行流程

### Phase1: 上下文收集

> 按需加载: 按 G7 按需读取表"DESIGN Phase1 按需"行，根据条件加载所需文件

> 核心职责: 纯信息收集，不做设计决策。为 Phase2（方案构思）提供完整、准确的项目上下文。
> 已有项目优先基于代码和知识库形成假设，只有低置信度且会影响执行路径的信息才追问用户。

#### 步骤1: 知识库开关检查

```yaml
KB_CREATE_MODE=0 → KB_SKIPPED=true
KB_CREATE_MODE=1 → KB_SKIPPED=false
KB_CREATE_MODE=2 → 编程任务→KB_SKIPPED=false | 非编程任务→KB_SKIPPED=true
KB_CREATE_MODE=3 → KB_SKIPPED=false
传递: Phase2 及 DEVELOP 阶段直接使用此值
```

#### 步骤2: 检查知识库状态

```yaml
前置: KB_SKIPPED=false 时执行

知识库状态显示:
  KB_CREATE_MODE=0: "⚠️ 已跳过（开关关闭）"
  存在: "✅ 已加载"
  MODE=1 不存在: "ℹ️ 不存在，已跳过（建议 ~init）"
  MODE=2 不存在: 编程任务→"🔄 已自动创建" | 非编程→同MODE=1
  MODE=3 不存在: "🔄 已自动创建"

MODE=1不存在 或 MODE=2非编程不存在:
  KB_SKIPPED=true
  继续执行
```

#### 步骤3: 初步复杂度评估

```yaml
评估: 按 G9 复杂度判定标准，基于已知信息初步设置 TASK_COMPLEXITY = simple | moderate | complex
依据: 需求描述中的工作单元数/涉及领域数/跨层级等维度（精确值待步骤5后确认）
脚本（可选）: project_stats.py

检测到 complex:
  输出: ℹ️ 复杂度: complex，将在方案构思阶段按实际派发结果判定是否启用子代理编排
  继续执行
```

#### 步骤4: 获取项目上下文

```yaml
KB_SKIPPED=true → 扫描项目现有资源（代码库/文档/素材）
KB_SKIPPED=false → 知识库优先，不足则扫描项目现有资源

项目环境配置:
  检测 {KB_ROOT}/project.yaml、runbook.yaml、secrets.local.yaml 是否存在
  存在 → 按需加载 services/project-env.md，提取环境角色、远程路径、验证命令和 protected 约束，作为实施条件与验证策略来源
  不存在 → 不阻塞；当任务涉及服务器、测试环境、生产环境、部署、远程日志或用户要求日常迭代命令时，提示可使用 ~ssh 初始化
  DO NOT: 在 DESIGN 阶段连接服务器或读取真实凭据

澄清模式:
  已有项目（假设模式，默认）:
    - 先读取知识库摘要 + 与当前需求直接相关的 5-15 个文件/配置/模板
    - 基于代码事实形成规划假设，标注置信度和证据来源
    - 仅当假设低置信度且影响实现路径、范围边界或验收方式时追问
  全新项目或信息不足（交互模式）:
    - 每次只问一个真正影响执行路径的问题
    - 优先给 2-4 个可执行选项，并标注推荐项和理由
    - 用户明确委托时，记录为“DESIGN 阶段按推荐方案补充”，继续推进

读取边界:
  - 不为规划展开全项目扫描；只读取与当前目标、约束、风险直接相关的文件
  - 不把任务类型隐式假设当作事实；假设必须来自用户输入、知识库或代码证据
  - 不在 Phase1 做技术选型或实现方案决策

子代理调用（按需自动编排，遵循自动编排原则 [→ G10]）:
  现有项目资源 + ≥2个可独立扫描的目录/模块 → 先按范围去空、去重、合并重叠职责并过滤强依赖/低收益项，重新计算最终扫描组数
  最终扫描组数 ≥2 → 按编排五步法调度子代理执行项目资源扫描（子代理数=最终扫描组数，≤6/批）[→ G10 调用通道]
    每个子代理 prompt 明确: 负责的目录路径 + 扫描内容（文件结构/入口点/导出接口/依赖关系）
    按 G10 有界等待规则收敛每个子代理：先记录复杂度预算，超时先强制请求 partial handoff，再按当前 CLI 的停止/回收协议收敛；所有代理进入终态后，主代理汇总实际返回内容并只补齐 pending_scope
  新建项目(目录为空或仅配置文件) 或 最终扫描组数 <2 → 主代理直接执行，不 spawn 单个子代理
```

#### 步骤5: 提取关键目标与成功标准

```yaml
从完整需求提炼核心目标，明确可验证的成功标准
必须提取:
  - 核心目标: 本次必须解决的问题
  - 范围边界: 包含内容与明确不做的内容
  - 成功标准: 可通过命令、文件检查、行为验证或人工核对确认的条件
  - 低置信度假设: 需要在 Phase2 方案中显式处理或追问的风险点
```

#### 步骤6: 深度分析与准备

```yaml
执行: 定位相关模块/素材 + 针对当前任务涉及的内容进行质量检查(过时信息/安全风险/一致性问题) + 问题诊断(日志/错误/冲突)
外部工具: 需要最新参考资料时按 G4 规则调用，保存/恢复 CURRENT_STAGE
输出物: 项目上下文（执行环境、项目结构、质量问题、约束条件）

假设验证:
  - 对每个关键假设给出证据来源（用户输入/知识库/代码文件/配置文件）
  - 与代码事实冲突时，以代码为准，并在 Phase2 写入风险或修正方案
  - 无法验证且会影响执行的假设 → INTERACTIVE 追问 | DELEGATED 选择保守推荐并记录

子代理调用（按需自动编排，遵循自动编排原则 [→ G10]）:
  ≥2个可独立分析的单元 → 先按范围去空、去重、合并重叠职责并过滤强依赖/低收益项，重新计算最终分析组数
  最终分析组数 ≥2 → 按编排五步法调度子代理执行深度依赖分析和质量评估（子代理数=最终分析组数，≤6/批）[→ G10 调用通道]
    每个子代理 prompt 明确: 负责的单元路径 + 分析内容（依赖关系/接口/质量问题/风险）
    按 G10 有界等待规则收敛每个子代理：已完成结果立即保留；超时代理先强制请求 partial handoff，再按当前 CLI 的停止/回收协议收敛；主代理汇总实际返回内容并按 pending_scope 补齐技术分析
  最终分析组数 <2 → 主代理直接执行，不 spawn 单个子代理

并行优化: 当步骤4和步骤6均需调用子代理且分析维度无交集时 → 并行调度 [→ G10 并行调度规则]
  否则 → 保持串行（步骤4先完成，结果传给步骤6）

复杂度确认: 根据完整分析结果修正 TASK_COMPLEXITY（若与步骤3初评不同则更新）

**DO NOT:** 做技术选型决策（留给 Phase2），设计实现方案（留给 Phase2），修改代码（留给 DEVELOP）
```

#### Phase1 完成

```yaml
输出: 上下文收集摘要（项目结构、关键目标、现有资源、约束条件）
继续: 直接进入方案构思与规划
```

### Phase2: 方案构思与规划

> 按需加载: 按 G7 按需读取表"DESIGN Phase2 按需"行加载所需文件

#### 步骤7: 模式分支判定

| 模式 | 特点 | 流程 | 子代理（概述，实际调用见各步骤） |
|------|------|------|--------|
| TASK_COMPLEXITY=simple（轻量） | 跳过方案包创建，输出轻量方案摘要 | → 轻量 DEVELOP | 无 |
| TASK_COMPLEXITY=simple/moderate | 跳过多方案对比，但必须记录唯一方案取舍 | → 步骤11 | 主代理直接填充方案包（步骤11） |
| TASK_COMPLEXITY=complex | 复杂任务多方案对比 | → 步骤8-13 | [RLM:brainstormer] 构思方案（步骤10）+ 主代理评估对比（步骤10）+ 主代理填充方案包（步骤11） |

```yaml
TASK_COMPLEXITY=simple 轻量路径:
  条件: TASK_COMPLEXITY=simple 且 涉及文件≤3 且 预估总改动行≤30
  行为:
    - 跳过 create_package.py、proposal.md、tasks.md、validate_package.py
    - 在 DESIGN 阶段输出轻量方案摘要（需求+方案+风险+验证方式，≤200字）
    - 设置 LIGHTWEIGHT_DESIGN = true
    - 直接进入 DEVELOP（不创建 CREATED_PACKAGE）
  回退: 条件不满足（文件>3 或 改动>30行）→ 走现有 simple/moderate 路径（创建方案包）
  KB同步: LIGHTWEIGHT_DESIGN=true 时 KB 同步降级为 R1 规则（CHANGELOG 快速修改分类）
```

#### 步骤8: 准备工作（仅 TASK_COMPLEXITY=complex）

```yaml
知识库检查: 使用 Phase1 已设置的 KB_SKIPPED 值
上下文获取: KB_SKIPPED=false→知识库读取 | KB_SKIPPED=true→扫描项目现有资源
项目规模判定: 使用 Phase1 已设置的 TASK_COMPLEXITY，影响任务拆分粒度
```

#### 步骤9: 分析判定（仅 TASK_COMPLEXITY=complex）

**项目场景判定:**

| 场景 | 特征 | 原则 | 填充深度 |
|------|------|------|----------|
| 新项目 | 初始化/从零开始 | 大胆创意，含需求视角分析 | 完整填充 |
| 现有项目 | 修改/优化/修复 | 精准执行，尊重现有成果 | 精简填充 |

**TASK_COMPLEXITY=complex = 多方案对比（强制，无例外）:**
TASK_COMPLEXITY=complex 任务的典型特征（多交付物/架构未定/技术选型/用户明确要求多方案）:
- 新项目初始化/重大重构/从零创建
- 架构决策/技术选型/方案选型
- 多种实现路径或内容组织方式
- 涉及多个模块/章节/领域
- 用户明确要求多方案

#### 步骤10: 方案构思与评估（仅 TASK_COMPLEXITY=complex）

⚠️ **串行强制:** 步骤10 整体与步骤11 之间串行:
步骤10: [RLM:brainstormer](各自独立构思方案，并行) → 主代理评估对比+标记推荐
步骤11: 主代理填充方案包
步骤10 与步骤11 之间有用户选择（INTERACTIVE）或自动选择（DELEGATED）

```yaml
TASK_COMPLEXITY=complex（CRITICAL）:
  方案构思: 优先调度 3~6 个 [RLM:brainstormer] 子代理（按需求复杂度决定数量），每个子代理独立构思一个差异化方案（并行）[→ G10 调用通道]
    - 派发前按编排五步法语义过滤空范围、重复/重叠职责和强依赖；最终可派发 brainstormer 少于 3 个时不得派发或声明启用，输出阻断错误（选项：修正方案职责后重试 / 取消流程）→ ⛔ END_TURN
      说明: 此处阻断仅因职责划分错误（可派发数不足），不属于运行时超时降级
    - 最终可派发数达到 3 后检查工具、角色、平台和并发能力；能力不足属于编排失败降级 → 记录可审计证据 → 进入「主代理降级构思」路径（禁止卡在“修复环境后重试”循环）
    - Codex CLI agent_type=brainstormer | Claude Code subagent_type="ha-brainstormer"
    - 以宿主工具真实返回统计实际成功启动数；仅实际成功启动 brainstormer ≥3 后，才可声明已启用子代理编排
    - 兼容重试后实际成功启动数 <3 → 自动编排未启用；立即请求已启动代理 partial handoff，并按当前 CLI 的停止/回收协议确认其不再扩展，保留有证据的完成范围、记录降级证据 → 进入「主代理降级构思」路径；禁止把主代理补全内容标记为子代理产出
    - 全部 spawn 后立即进入 G10 有界等待（Codex CLI: collab wait，Claude Code: Task/后台代理）；按每个方案复杂度独立计算预算，超时先强制请求 handoff，再按当前 CLI 的停止/回收协议收敛；等待期间禁止生成未返回代理的方案内容，也禁止在代理仍可能扩展时重叠写入同一方案范围
    - 每个子代理接收相同的 Phase1 上下文 + 评估阶段确认的需求信息（含用户选择的成果规格偏好），独立输出方案（名称、核心思路、实现路径、成果设计（呈现方向/风格/体验）、用户价值、优缺点）
    - 子代理之间不共享中间结果，确保方案差异化（实现路径和成果设计方向均须差异化，不得仅路径不同而呈现方向趋同）。用户已在评估阶段确认的实施条件（如技术栈/工具/平台）各方案须遵守，差异化体现在架构模式/组件设计/内容组织/呈现策略等层面
    - UI 任务子代理额外约束: "方案须包含具体视觉设计方向（配色/布局/组件风格/动效），不能仅描述功能实现。视觉方向须差异化。"
  方案产出门槛（优先子代理，失败可降级）:
    - 成功路径: 进入比较前优先收集至少 3 个由不同代理返回的可用方案，每个方案均包含名称、核心思路、实现路径、成果设计、用户价值和优缺点
    - partial 规则: 只允许主代理补齐已有方案中证据明确的局部缺口；不得从空 pending_scope 生成整套“子代理方案”，不得伪造 source=subagent
    - 降级触发: 可用方案少于 3 个（超时 / 失败 / 无有效 handoff / 启动不足）且已按 G10 收敛代理并记录可审计证据 → 进入「主代理降级构思」，禁止 ⛔ END_TURN 仅提示重试/取消
  主代理降级构思（CRITICAL）:
    触发: 能力不足 | 实际成功启动数 <3（有证据）| 启动 ≥3 但可用方案 <3（timeout_no_handoff / failed / 无效 handoff）
    执行:
      1. 确认所有相关代理已进入 completed/failed/partial handoff/closed 或 CLI 等价终态
      2. 保留子代理已返回的可用方案，标注 source=subagent
      3. 主代理基于 Phase1 上下文补齐差异化方案至可比较集合（目标 ≥3）；若时间/上下文不足以形成多方案，允许产出唯一方案，但必须写完整取舍（放弃路径+原因）
      4. 主代理补齐的方案标注 source=main_agent_fallback，并在后续 proposal.md 方案取舍与相关 tasks 标注 [降级执行]
      5. 记录降级证据: agent id（如有）、wait_budget_seconds、handoff 结果、timeout_no_handoff/spawn 错误、能力检测结果
    禁止: 静默跳过多方案且不记证据 | 把 main_agent_fallback 伪造成 subagent | 在代理未收敛前重叠执行同一 pending_scope
  方案评估: 所有相关代理进入终态后，合并 source=subagent 与 source=main_agent_fallback 的可用方案，主代理统一评估对比并标记"推荐"；未返回且无降级补齐的方案不编造内容
    推荐标记: 推荐必须标记成果最完善、体验最好的选项，而非最简化最易实现的选项。推荐选项默认排序号1，（推荐）标记置于选项文本末尾
    评估维度: 用户价值（实用性/体验/现代使用场景）、方案合理性（专业性/可行性/可持续性/延展性）、风险(含EHRB)、实施成本（复杂度/工作量）
    权重: 按项目上下文动态调整（如性能关键系统提升方案合理性权重，原型/MVP 提升实施成本权重，品牌设计提升用户价值权重），用户价值始终不低于其他单项
    UI 任务权重修正: 交付物含 UI 时，"用户价值"中的"体验"子维度权重提升（视觉完成度、交互丰富度、布局专业度作为显式评估子维度参与加权）
    主代理基于完整上下文直接综合评估结果（不通过子代理中转）
  INTERACTIVE → 输出方案对比（含 source 标注与降级说明如有）→ ⛔ END_TURN（等待用户选择方案N / 重新构思 / 取消(→状态重置)）
    用户选择后:
      方案N → 确认选择，进入步骤11
      重新构思 → 回到步骤10 重新调度子代理构思方案（最多重试 1 次，仍不满意则取消）
      取消 → 状态重置
  DELEGATED → 推荐方案直接进入步骤11（降级路径同样自动选推荐，不因降级打断委托）

TASK_COMPLEXITY=simple/moderate:
  直接确定唯一方案 → 步骤11
  必须在 proposal.md 记录:
    - 为什么该方案是当前最合理路径
    - 放弃的替代路径及原因
    - 风险、回滚边界和验证策略
  不得因为跳过多方案对比而省略取舍说明
```

**INTERACTIVE 输出要素（按 G3 格式包装，场景=确认 ❓）:**
```yaml
主体内容:
  上下文收集摘要（项目结构、关键目标、现有资源、约束条件）
  （空行）
  方案对比（每个方案用 - 标记，非数字编号：名称、核心思路、成果设计方向、优缺点、推荐标记、source）
  （空行）
  降级说明（如有）: 触发原因 + 证据摘要 + [降级执行]
  （空行）
选项:
  选项：
  1~N. 各方案名称（推荐方案排序号1并标记推荐），N = 实际方案数
  N+1. 重新构思
  N+2. 取消
下一步引导: 引导用户回复选项编号，说明确认后进入详细规划并开始开发实施
```

**DO:** 所有方案详情完整输出后才提供选择；能力可用时必须先派发 brainstormer；超时/失败有证据后主代理降级继续，不阻断委托

**DO NOT:** 在方案详情输出前提供选项；在子代理仍可能扩展时生成重叠方案内容；把主代理降级方案伪造成子代理产出；在可用方案不足且无证据时静默跳过；因超时/启动失败反复 ⛔ END_TURN 要求用户“修复环境后重试”

#### 步骤11: 详细规划

```yaml
脚本: create_package.py <feature> [--type <implementation|overview>]
目录创建: 按 G1 写入策略自动创建

脚本返回 success=false → 按 rules/tools.md AI降级接手流程处理

填充步骤:
  1. create_package.py 创建目录和模板
  2. 处理执行报告
  3. 主代理按 PackageService 接口规范直接填充 proposal.md（按场景深度）:
     必须包含:
       - 需求、目标、约束、验收标准
       - 技术方案、影响范围、风险评估
       - 方案取舍: 唯一方案理由、放弃的替代路径、回滚边界
       - 验证策略: verifyMode(test-first|review-first)、reviewerFocus、testerFocus、UI验证要求、风险边界
     说明: 验证策略写入 proposal.md，不新增 v3.0 contract.json 或 .ralph-* 状态文件
  4. 主代理按 PackageService 接口规范直接填充 tasks.md（元数据头部+任务清单+状态符号+依赖声明）
     每个任务必须包含:
       - 文件路径或明确作用范围
       - 预期变更
       - 完成标准
       - 验证方式
       - depends_on 字段，声明前置依赖任务编号 [→ G10 DAG 依赖调度]
     推荐格式:
       - [ ] 1.1 修改 `path/to/file`
         - 预期变更: ...
         - 完成标准: ...
         - 验证方式: ...
         - depends_on: []
  5. UI 决策边界（含视觉产出的任务，写入 proposal.md "成果设计" 节）:
      决策层级:
        - 本次 feature 的 UI 决策写入 proposal.md
        - 跨 feature 稳定成立的项目级设计契约才同步到知识库或 DESIGN.md（若项目存在该文件）
        - 当前方案包中的 UI 决策优先于通用 UI 基线
      禁止: 把一次性页面细节写成项目级长期契约
  6. 成果设计（含视觉产出的任务，填充 proposal.md "成果设计" 节）:
      设计思维（写代码前必须完成的创意决策，CRITICAL）:
        - 目的与受众: 谁在用？什么场景？什么情绪？
        - 美学基调: 选择鲜明方向，提交到一个明确的美学立场
          方向空间: 极简精致/大胆鲜艳/暗色科技/温暖有机/复古怀旧/游戏化活泼/
                    编辑杂志/粗犷原始/奢华精致/工业实用/像素复古/手绘插画...
          CRITICAL: 每个设计必须有明确的美学立场。大胆的最大化和精致的最小化都好，
                    关键是意图明确，而非强度。
        - 记忆点: 用户看到这个设计时会记住的一个特征
      视觉要素输出（写入 proposal.md "成果设计" 节）:
        - 配色: 大胆的主色+锐利的强调色优于胆怯的均匀分配，提交到一个有凝聚力的色彩体系
        - 字体: 有个性的展示字体(标题)+精致的正文字体配对，避免 Arial/Inter/Roboto 等通用字体
        - 布局: 非对称/重叠/对角线流动/破格元素/留白或密度控制 — 有意识的空间运用
        - 动效: 高影响时刻优先（一个精心编排的入场动画 > 散落的微交互），状态切换/滚动触发/交互反馈的动态效果
        - 氛围: 渐变/噪点纹理/几何图案/透明叠层/戏剧性阴影/装饰性边框/颗粒覆盖 — 创造纵深感而非默认纯色背景
      来源优先级:
        用户明确指定的视觉参考 > 步骤10子代理方案中用户选择的方向(TASK_COMPLEXITY=complex)
        > 从目的×受众×场景推导（推导时禁止使用"现代简洁"等空泛默认值）
      禁止: 通用AI美学（通用字体、紫色渐变白底、千篇一律卡片布局、
            无个性灰白配色、所有设计长得一样）
      跨次变异: 每次设计在明暗主题/字体/美学方向间变换，不同任务绝不趋同
      匹配原则: 实现复杂度须匹配美学愿景 — 大胆设计需要丰富代码，
               精致设计需要克制和精确
      创造力释放: 不要保守，突破常规，展现真正有设计感的作品
      非视觉任务: 跳过本步骤
  7. 技术约束（选填 proposal.md "技术约束" 部分）:
      可访问性/响应式/性能 — 仅列硬性约束，无则留空
  8. 设置 CREATED_PACKAGE
```
